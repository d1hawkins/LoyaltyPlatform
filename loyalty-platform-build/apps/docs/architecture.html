Multi-Tenancy Model

The platform uses a database-per-tenant isolation model. Every tenant gets their own SQL Server database with identical schema, ensuring complete data isolation.

Tenant Resolution

Every request must include a tenant identifier. In production, the tenant is extracted from the JWT tenantId claim. In dev mode, it comes from the X-Tenant-ID header.

Request --> APIM --> JWT validation --> Extract tenantId claim

                                    Control Plane DB lookup
                                              |

                                              |

Service Architecture

Member Service (Port 3001)

Handles enrollment, profile management, member lookup, and GDPR operations. PII (email, phone) is encrypted at rest with AES-256-GCM with per-field random IV. Lookups use HMAC-SHA256 hashes with per-tenant peppers.

  • Hot path: phone lookup at p99 < 100ms @ 500 RPS
  • Balance served from Redis cache (300s TTL)
  • Publishes: member.enrolled, member.updated, member.deleted

Loyalty Engine (Port 3002)

Transaction processing with atomic writes. Every transaction creates an immutable ledger entry in the same database transaction. The points calculator is a pure function with configurable base rates, tier multipliers, and category bonuses.

  • All writes require Idempotency-Key header (24h retention)
  • Immutable ledger -- no UPDATE/DELETE on points_ledger (enforced by DB trigger)
  • Points expiry with configurable TTL and notification reminders
  • Built-in fraud detection (velocity checks, pattern matching, configurable rules)
  • Publishes: points.earned, points.redeemed, transaction.voided

Offer Service (Port 3004)

Offer catalog management, personalized eligibility engine, code generation, and redemption workflow.

  • 10-rule eligibility engine evaluating tier, points, status, and limits
  • Bulk code generation with configurable prefixes
  • Coordinates with Loyalty Engine for point deductions on redemption

Admin API (Port 3005)

30 endpoints for program configuration, tier management, webhook CRUD, API key management, feature flags, branding, and audit logging.

  • Three-role RBAC: owner, manager, analyst
  • Full audit trail with before/after JSON diffs
  • CSV export for members and audit logs

Webhook Worker (Port 3009)

Reliable outbound delivery of platform events to tenant-registered HTTP endpoints.

  • Durable delivery table with exactly-once DB persistence
  • HMAC-SHA256 signed payloads
  • Exponential backoff retry (30s, 2m, 10m, 1h, 6h)
  • Dead-letter queue with manual replay

Event-Driven Design

Services communicate asynchronously via Azure Service Bus topics. Each event is wrapped in a standard EventEnvelope:

  "eventId": "uuid",
  "eventType": "points.earned",
  "tenantId": "uuid",

Data Model

Control Plane Database

Shared across all tenants. Stores tenant metadata, API keys, and feature flags.

  • tenants -- tenant registry with database connection info
  • tenant_api_keys -- bcrypt-hashed API keys
  • feature_flags -- per-tenant feature toggles

Tenant Database (per-tenant)

Each tenant has their own database with these core tables:

  • members -- encrypted PII, status, tier assignment
  • tiers -- tier definitions with multipliers and thresholds
  • transactions -- purchase records
  • points_ledger -- immutable, append-only ledger entries
  • program_config -- earn rates, void window, expiry settings
  • offers -- offer catalog with targeting rules
  • redemptions -- redemption records
  • offer_codes -- generated redemption codes
  • webhook_configs -- registered webhook endpoints
  • webhook_deliveries -- delivery tracking with retry state
  • audit_log -- admin action audit trail
  • fraud_flags -- suspicious activity records
  • fraud_rules -- configurable fraud detection rules

Security

  • PII Encryption: AES-256-GCM with per-field random 96-bit IV. Version-tagged for key rotation support.
  • Lookup Hashing: HMAC-SHA256 with per-tenant pepper derived from base pepper. Not comparable across tenants.
  • Webhook Signing: HMAC-SHA256 with per-webhook shared secret. Timestamp included to prevent replay attacks.
  • API Keys: bcrypt-hashed, plaintext returned only once at creation.
  • GDPR: Soft delete with T+30d hard scrub. Data export endpoint. Audit trail for all deletions.
  • Fraud Detection: Real-time velocity checks in Redis hot path (<20ms overhead). Configurable rules per tenant.

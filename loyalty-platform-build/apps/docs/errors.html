Errors & Rate Limits

All errors follow the RFC 7807 Problem Details standard. Rate limits are enforced at the APIM gateway level.

RFC 7807 Error Format

Every error response uses the application/problem+json content type and follows the RFC 7807 structure:

{
  "type": "about:blank",
  "title": "Validation Error",
  "status": 400,
  "code": "VALIDATION_ERROR",
  "detail": "\"phone\" is required",
  "instance": "/member/v1/members"
}

Some errors include additional context fields:

{
  "type": "about:blank",
  "title": "Duplicate Member",
  "status": 409,
  "code": "DUPLICATE_MEMBER",
  "detail": "A member with this phone number already exists",
  "existingMemberId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}

import { LoyaltyError, RateLimitError } from '@loyalty/loyalty-js-sdk';

try {
  await client.recordTransaction({ ... });
} catch (err) {
  if (err instanceof RateLimitError) {
    // err.retryAfterMs tells you when to retry
    await sleep(err.retryAfterMs);
    // SDK also handles retries automatically (maxRetries: 2)
  }
}

Rate Limiting

APIM Gateway Limits

ScopeLimitWindow
Per subscription key1,000 requests1 minute

When rate-limited, the gateway returns:

{
  "statusCode": 429,
  "message": "Rate limit is exceeded. Try again in X seconds."
}
Consumption Tier
The current APIM deployment uses the Consumption tier, which applies rate limits per gateway instance. For more granular per-tenant rate limiting, upgrade to the Developer or Premium tier.

SDK Retry Behavior

The JavaScript SDK automatically retries on 429 and 5xx responses:

  • Default: 2 retries with exponential backoff (500ms, 1000ms)
  • Configurable via maxRetries in the client constructor
  • Non-retriable errors (400, 401, 403, 404, 409, 422) are thrown immediately

Idempotency

All write endpoints on the Loyalty Engine require an Idempotency-Key header.

BehaviorDescription
Same key + same bodyReturns the original response (replay)
Same key + different body409 Conflict
Key expiry24 hours
ScopePer-tenant (isolated across tenants)
Failed requestsKey is NOT stored on failure, allowing safe retry
 
# Idempotent transaction -- safe to retry
curl -X POST https://loyalty-dev-apim-5rdrqh.azure-api.net/engine/v1/transactions \
  -H "Content-Type: application/json" \
  -H "Ocp-Apim-Subscription-Key: YOUR_KEY" \
  -H "X-Tenant-ID: YOUR_TENANT_ID" \
  -H "Idempotency-Key: order-12345" \
  -H "X-Skip-Auth: true" \
  -d '{ "memberId": "...", "channel": "pos", "amount": 1500, "currency": "USD" }'
Missing Idempotency-Key
Submitting a POST to /engine/v1/transactions without the Idempotency-Key header will return 400 VALIDATION_ERROR at the APIM gateway level before the request reaches the backend.

Correlation IDs

Every request through APIM receives a X-Correlation-ID header in the response. Include this ID when contacting support for faster debugging.

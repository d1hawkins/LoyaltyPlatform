Authentication

The platform supports Azure AD B2C tokens, APIM subscription keys, and a dev-mode bypass for local development.

Authentication Layers

Every API request passes through two layers of authentication:

LayerMechanismPurpose
API Gateway (APIM)Ocp-Apim-Subscription-Key headerIdentifies the calling application and enforces rate limits
Service AuthAuthorization: Bearer {JWT}Identifies the user/service and resolves the tenant

APIM Subscription Keys

All requests through the API gateway require a subscription key in the Ocp-Apim-Subscription-Key header.

curl https://loyalty-dev-apim-5rdrqh.azure-api.net/member/v1/members \
  -H "Ocp-Apim-Subscription-Key: YOUR_KEY_HERE"

Keys are scoped to the loyalty-b2b product. The current rate limit is 1,000 requests per minute per subscription.

Retrieving Your Key

# List subscriptions
az rest --method get \
  --url "https://management.azure.com/subscriptions/13e630db-.../providers/Microsoft.ApiManagement/service/loyalty-dev-apim-5rdrqh/subscriptions?api-version=2022-08-01"

# Get keys for a specific subscription
az rest --method post \
  --url "https://management.azure.com/.../subscriptions/loyalty-b2b-dev/listSecrets?api-version=2022-08-01"

Azure AD B2C (Production)

In production, all requests must include a valid B2C JWT token. The platform uses two B2C flows:

B2B (Server-to-Server)

For backend integrations using the Client Credentials flow.

SettingValue
PolicyB2C_1A_ClientCredentials
Audienceapi://loyalty-b2b
Scopesmembers.read, members.write, transactions.write, admin
 
# Acquire a B2B token
export B2C_TENANT_NAME=loyaltyplatformdev
export B2C_B2B_CLIENT_ID=your-client-id
export B2C_B2B_CLIENT_SECRET=your-client-secret
./infra/b2c/acquire-b2b-token.sh

Consumer (Mobile / End-User)

For mobile apps and consumer-facing flows using PKCE.

SettingValue
PolicyB2C_1A_SignUpOrSignin
Audienceapi://loyalty-consumer
Scopesopenid, profile, offline_access, member.self
Redirect URIsloyalty://callback, https://localhost:3000/callback

Additional B2C Policies

  • B2C_1A_PasswordReset -- password reset flow
  • B2C_1A_ProfileEdit -- profile edit flow

JWT Claims Used

Services extract the following from validated tokens:

ClaimMapped ToPurpose
subX-User-IDIdentifies the authenticated user
tenantIdX-Tenant-IDTenant scoping for data isolation
rolesRole-based accessAdmin API RBAC (owner / manager / analyst)

Dev Mode (SKIP_AUTH)

For local development and testing, services can bypass JWT validation entirely.

Development Only
SKIP_AUTH=true must never be enabled in staging or production environments. The CI/CD pipeline enforces this check.

Service-Level Bypass

When a service is started with SKIP_AUTH=true, it trusts these headers instead of JWT claims:

curl http://localhost:3001/v1/members \
  -H "X-Tenant-ID: 11111111-1111-1111-1111-111111111111" \
  -H "X-User-ID: dev-user"

For admin endpoints, also include:

curl http://localhost:3005/v1/admin/tiers \
  -H "X-Tenant-ID: 11111111-1111-1111-1111-111111111111" \
  -H "X-User-ID: dev-user" \
  -H "X-User-Role: owner"

APIM Gateway Bypass

When calling through the APIM gateway, add the X-Skip-Auth header. APIM strips this header before forwarding to the backend service:

curl https://loyalty-dev-apim-5rdrqh.azure-api.net/member/v1/members \
  -H "Ocp-Apim-Subscription-Key: YOUR_KEY" \
  -H "X-Skip-Auth: true" \
  -H "X-Tenant-ID: 11111111-1111-1111-1111-111111111111"

Required Headers Summary

HeaderRequiredDescription
Ocp-Apim-Subscription-KeyAlways (via APIM)APIM subscription key
AuthorizationProductionBearer {JWT}
X-Tenant-IDAlwaysTenant UUID
X-Skip-AuthDev only (APIM)Bypasses JWT validation at gateway

RBAC Roles (Admin API)

The Admin API uses three role levels sourced from the JWT roles claim:

RoleAccess Level
ownerFull access: API keys, tier create/delete, feature flags, GDPR confirm
managerMember management, webhooks, offers, points adjustments, branding
analystRead-only: members, tiers, audit log, branding
